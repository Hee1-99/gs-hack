# GStep 계정과 매장 연결

이 앱은 `@supabase/supabase-js`로 아이디/비밀번호 인증과 매장 데이터를 연결합니다. 설정이 없으면 로그인 화면에 체험 모드를 명시하고 기존 브라우저 저장 기능을 제공합니다. 로그인한 계정의 데이터와 체험 기록은 자동으로 합치지 않습니다.

## 연결 순서

1. **GStep 용도로 확인된 프로젝트에서만** `migrations/202609210001_gstep_team_auth.sql`을 SQL Editor 또는 Supabase CLI로 적용합니다. 이 마이그레이션은 새 GStep 테이블을 만들며 기존 앱 테이블을 변경하지 않습니다.
2. 프로젝트 Authentication 설정에서 Email provider를 활성화하되 **Confirm email을 끕니다**. 앱은 아이디를 내부 예약 주소 `<소문자아이디>@id.gstep.invalid`로 매핑하여 SDK를 사용합니다. 사용자에게 이메일을 요청하거나 표시하지 않습니다. 가입 직전 공개 Auth 설정을 조회하여 `mailer_autoconfirm: true`일 때만 요청을 보내므로, 이메일 확인 설정이 켜졌거나 설정 조회가 실패하면 가입을 차단합니다. 이 내부 주소로 확인 메일을 발송하는 흐름을 만들지 않습니다.
3. `.env.local` 또는 배포 환경에 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`를 설정하고 다시 빌드합니다. 기존 공개 anon JWT는 `NEXT_PUBLIC_SUPABASE_ANON_KEY`로도 읽습니다. 브라우저에는 공개 키만 사용하며 `service_role` 또는 `sb_secret_` 키는 사용하지 않습니다. 키 값을 문서, 로그, 커밋에 넣지 않습니다.
4. `/login`에서 경영주 아이디를 가입·로그인하고 새 매장을 만듭니다. 해당 계정은 **직접 만든 새 매장**에만 경영주 권한을 갖습니다.
5. 경영주 계정 화면에서 초대 코드를 만듭니다. 스토어 매니저는 별도 아이디를 가입하고 초대 코드로 연결합니다. 코드는 24시간 동안 한 번만 사용할 수 있습니다. 서버에는 코드의 SHA-256 해시만 저장됩니다.

아이디는 영문·숫자·밑줄(_) 4~24자이며 대소문자를 구분하지 않습니다. 비밀번호는 8자 이상입니다. 이메일 인증·이메일 비밀번호 복구 기능은 제공하지 않습니다. 기존 이메일 방식 계정의 아이디 자동 이전은 포함하지 않습니다.

현재 모델은 계정 하나당 매장 하나입니다. 매장 이동·탈퇴·복수 경영주 위임 기능은 포함하지 않습니다. 사용자 수정 가능 메타데이터는 권한 판정에 사용하지 않습니다.

## 저장과 권한

| 데이터 | 스토어 매니저 | 경영주 |
|---|---|---|
| 매장 이름·규칙·체크리스트 항목 | 소속 매장 읽기 | 소속 매장 읽기, 설정 RPC로 변경 |
| 체크리스트 상태·Q&A 기록 | 본인만 읽기·저장 | 소속 직원 읽기, 본인 상태 저장 |
| 퀴즈·고객응대 연습 기록 | 본인만 읽기·저장 | 소속 직원 읽기, 본인 연습 저장 |
| 소속·역할 | 본인 소속 읽기 | 소속 매장 직원 읽기 |

RLS와 명시적인 테이블 권한, `auth.uid()` 기반 RPC가 서버에서 강제합니다. 클라이언트의 화면 차단은 보조 수단입니다. 경영주도 다른 사람의 점수를 직접 수정할 수 없습니다. 점수는 교육 피드백이며 변조 방지 시험 인증이나 자동 채용 판단을 제공하지 않습니다.

공유 설정과 개인 체크리스트에는 버전을 사용합니다. 다른 기기의 변경 이후 이전 버전으로 저장하면 덮어쓰는 대신 오류가 표시됩니다. 새로고침 후 다시 저장해야 합니다. 원격 저장에 실패한 공유 설정은 성공한 것처럼 표시하지 않습니다. 퀴즈 기록은 계정별 브라우저 사본을 유지하며 다시 동기화할 수 있습니다. 최신 다른 기기 기록은 화면에 다시 방문하거나 새로고침하면 읽습니다.

## 검증

```powershell
npm test
npx tsc --noEmit
npm install --prefix .vercel/sql-verification --no-save --no-package-lock @electric-sql/pglite
node supabase/verify-rls.mjs
```

`verify-rls.mjs`는 네트워크 프로젝트에 연결하지 않고 PGlite PostgreSQL 엔진에 `auth.users`와 `auth.uid()` 테스트 구성을 만듭니다. 원본 마이그레이션을 pgcrypto와 함께 그대로 실행한 뒤 경영주 2명·직원 2명·외부 사용자·익명 권한을 바꿔 실제 SQL을 검증합니다. 매장 간 읽기 차단, 사용자/매장 ID 위조, 직원의 설정 변경, 다른 직원 점수 수정, 버전 충돌, 초대 재사용을 검사합니다.

2026-09-22 로컬 SQL 11개 검증 통과. 이는 **실제 Supabase 서비스 연결 검증이 아닙니다**. 사용자가 지정한 `mkfzkhirsjakjpqqcfcx.supabase.co`에 공개 키로 읽기 전용 확인을 실행했습니다. 사용자 SQL 적용 및 설정 변경 후 재확인 결과 Auth 설정 HTTP 200, 이메일 가입 활성, `mailer_autoconfirm: true`(이메일 확인 불필요)입니다. GStep 테이블 5개는 모두 HTTP 401 / `42501`로 익명 읽기가 거부되며 이전의 없는 테이블 `404/PGRST205` 상태가 해소됐습니다. 이는 테이블 존재·익명 접근 거부 확인이며, 가입/역할별 원격 데이터 저장 검증과는 구분합니다. 이 읽기 전용 확인에서는 계정 생성이나 이메일 발송을 하지 않았습니다.

실제 연결 후에는 서로 다른 브라우저 프로필로 경영주 A/직원 A와 경영주 B/직원 B를 만들고 다음을 확인해야 합니다.

- 아이디/비밀번호 가입 → 즉시 로그인 → 로그아웃 → 재로그인 및 새로고침 유지. 확인 메일 안내가 없어야 합니다.
- A의 초대로 가입한 직원의 퀴즈·응대 점수가 경영주 A에게만 표시됨.
- 경영주 A의 규칙/체크리스트 변경이 직원 A에게 보이고 B에게는 보이지 않음.
- 직원 A의 체크리스트 진행 상태가 직원 B의 상태에 영향을 주지 않음.
- 직접 SDK 요청으로 역할 변경, 다른 사용자 기록 upsert, 다른 매장 RPC 호출이 거부됨.
- 네트워크 단절/세션 만료 시 저장 실패를 알리고 로그인 상태에서 체험 데이터로 넘어가지 않음.

공식 참고: [Supabase 이메일 가입](https://supabase.com/docs/reference/javascript/auth-signup), [비밀번호 로그인](https://supabase.com/docs/reference/javascript/auth-signinwithpassword), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

### 실제 프로젝트 검증 — 2026-09-22

이후 합성 계정 4개, 분리된 검증용 매장 2개, 퀴즈 기록 2개로 SDK 검증 10개를 통과했습니다. 인증 확인 없이 가입, 역할 메타데이터 위조 무시, 매장·사용자 읽기 분리, 경영주 설정 공유, 직원/다른 매장의 설정 쓰기 거부, 체크리스트 영속성, 기록 사용자·매장 위조 거부, 경영주 조회, 독립 재로그인 후 조회를 확인했습니다. 계정은 `id.gstep.invalid` 예약 주소를 사용하며 실제 사용자 자료나 메일을 사용하지 않았습니다. 검증용 자격 증명은 Git에서 제외된 로컬 파일에만 보관합니다.

배포된 실제 브라우저에서도 아이디 가입 → 즉시 로그인 → 새 매장 생성 → 로그아웃·재로그인을 확인했습니다. 이 가입 검증으로 합성 계정·매장을 각각 하나 추가했습니다(합계 5계정·3매장). 스토어 매니저의 실제 6단계 연습 100점과 체크리스트 상태가 원격 저장되고 독립 경영주 브라우저에 표시됐으며, 다른 매장 경영주는 조회할 수 없었습니다. Gemini 고객 대화의 응답·70점 평가도 원격 저장·새로고침 복원·경영주 조회를 확인했습니다. 캡처는 `docs/evidence/gstep-account-*.png`입니다.

추가 낡은 버전 충돌 요청의 라이브 검사는 미완료입니다. `gstep_save_content`의 예상 `40001` 대신 20초 제한에서 status 0을 받았고, 세 번의 직접 실행 후 재시도를 중단했습니다. SDK 재시도 해제를 포함했지만 원인은 확정하지 않았습니다. 해당 요청의 전후 DB 비교는 수행하지 않았으므로 무변경을 입증했다고 주장하지 않습니다. 동일 SQL의 로컬 충돌 검사는 통과했으며, 정상 저장·권한 분리 라이브 성공과 이 미검증 항목을 구분합니다. 동시에 설정을 수정할 경우 새로고침 후 다시 저장하는 경로를 사용하세요.
